# C 系统编程学习路线

从最小可运行的教学实现出发，逐步理解软件系统中的执行、通信、存储、渲染、资源管理和代码生成机制。

本仓库不追求一次性复刻成熟产品，而是通过可观察、可测试、可解释的小项目，建立对底层系统的整体理解，并明确教学实现与生产系统之间的边界。

## 六大方向

### 01 · 编程基础设施

**Programming Infrastructure**

研究软件执行、内存管理、并发和运行时机制。

- 线程池、线程安全队列
- 内存池、对象池、协程调度器
- 定时器、事件循环
- 用户态任务调度与同步原语

**核心问题：程序如何执行，任务如何调度，资源如何管理？**

### 02 · 网络与分布式系统

**Networking & Distributed Systems**

研究机器之间如何通信、协调与传递数据。

- TCP 服务端、HTTP 服务器
- 简化版 Redis、Nginx
- 消息队列、发布订阅系统
- RPC 框架、服务发现
- 限流、重试、故障恢复

**核心问题：如何让独立运行的进程和机器可靠地协作？**

### 03 · 数据库与存储引擎

**Databases & Storage Engines**

从数据结构逐渐进入持久化、查询处理与事务系统。

- 哈希索引、B+ 树
- 页面管理与缓冲池
- WAL、崩溃恢复
- SQL 解析器与执行器
- MVCC、事务隔离
- 简化版关系型数据库

**核心问题：如何高效、可靠地存储和查询数据？**

### 04 · 浏览器与运行时

**Browser Engines & Runtimes**

研究网页如何从文本变成屏幕上的像素，以及脚本如何执行。

- HTML 解析器与 DOM
- CSS 解析、样式计算与布局
- 绘制与光栅化
- JavaScript 词法分析、解析与解释器
- 垃圾回收与运行时
- 浏览器进程模型与 IPC

**核心问题：浏览器如何把网页变成可交互的视觉界面？**

### 05 · 操作系统与 Linux 内核

**Operating Systems & Kernel Internals**

深入用户态与内核态的边界，以及硬件资源的管理。

- ELF 加载与进程启动
- 系统调用与上下文切换
- 进程调度与虚拟内存
- 页表、缺页异常
- 中断、设备驱动
- 文件系统与块设备
- 一个逐步演进的教学操作系统

**核心问题：操作系统如何管理硬件，并为应用程序提供运行环境？**

### 06 · 编译器与开发工具链

**Compilers & Toolchains**

研究源代码如何被转换为可执行程序。

- 词法分析器与语法分析器
- AST 与中间表示
- 简化版编译器
- 汇编、链接与 ELF
- 调试器、符号表
- 垃圾回收与代码生成策略

**核心问题：高级语言如何转化为机器能够执行的指令？**

## 三条原则

### 1. 每个项目都从最小可运行版本开始

例如，浏览器内核不应该从完整的 HTML、CSS、JavaScript 标准开始。

可以先实现一个极小的 HTML 解析器，再构建 DOM 树，然后实现简单的 CSS 选择器、布局计算与绘制。每个阶段都有可观察的输出，最后才逐渐组合成浏览器引擎。

数据库、消息队列和操作系统也遵循同样的思路。

### 2. 不只实现功能，还要解释设计选择

以消息队列为例，值得研究的不仅是发送和接收消息，还包括：

- 消息究竟存储在内存还是磁盘？
- 消费者处理失败后，消息如何重新投递？
- 怎样实现持久化与崩溃恢复？
- 消费确认与重复投递有什么关系？
- 消息顺序与并发消费如何权衡？

这些才是一个系统真正困难的地方。

### 3. 每个项目都要明确教学实现与生产系统的差距

纯 C、零第三方依赖是很好的教学约束，但不能成为牺牲正确性的理由。

可以自己实现核心机制，同时使用操作系统 API、编译器、调试器和测试工具。对于复杂项目，还应该明确哪些能力没有实现、哪些安全假设成立，以及哪些限制使它不适合生产环境。

特别是 Linux 内核和浏览器内核，它们都包含大量复杂的硬件、平台、安全和兼容性问题。可以从教学子集入手，而不是一开始就把目标定为复刻完整的成熟产品。

## 架构决策

**共享基础设施，但不要强行共享所有实现。**

可以单独维护一个 C 语言基础组件仓库：

- `containers`：链表、哈希表、动态数组等数据结构。
- `memory`：内存分配器与内存池。
- `concurrency`：线程池、同步工具。
- `network`：Socket 封装与基础网络工具。
- `testing`：测试辅助工具。

共享目标是复用稳定、通用且经过测试的机制，而不是把所有项目耦合成一个庞大框架。每个系统仍应保留清晰的边界，允许使用最适合当前问题的数据结构、并发模型和抽象层次。

## 教学方法

### 主流工程实现对比（Compare）

研究成熟项目的架构、数据结构、并发模型、存储格式与设计取舍。

例如，比较 Kafka 与 RabbitMQ 的消息模型差异，以及 PostgreSQL 与 SQLite 的事务和部署模型差异。

**回答：为什么不同团队会选择不同的实现？**

### 性能与设计验证（Evaluate）

通过基准测试、故障注入、源码分析和实验，验证不同架构的优缺点。

例如，比较不同消息存储方式的吞吐量、不同索引结构的查询性能、不同网络 I/O 模型的资源占用。

**回答：这种设计在什么条件下更合适？**

## 文章写作方法

1. **明确问题与使用场景**

   先确定系统解决什么问题，以及需要满足的延迟、吞吐量、持久化和一致性要求。

2. **阅读官方架构文档与源码**

   先理解官方描述的架构，再追踪关键数据结构、调用链和状态转换。源码版本要明确，避免把不同版本的实现混在一起。

3. **绘制自己的架构图**

   展示请求路径、数据流、线程模型、存储布局和关键组件之间的关系。

4. **建立公平的对比维度**

   固定测试条件，明确哪些功能、可靠性保证和配置保持一致，避免用不等价的实验得出结论。

5. **提出并验证设计假设**

   用源码证据、官方文档、可复现实验或基准测试，验证为什么某个方案在特定条件下更合适。

6. **给出有边界的结论**

   解释方案的优势、成本、局限，以及什么条件改变后结论可能不再成立。

## 项目约定

每个项目至少包含：

- **可运行的最小版本**：能够编译、运行，并提供明确的输入和输出。
- **设计说明**：解释数据结构、状态转换、并发策略和关键取舍。
- **测试与实验**：覆盖正常路径、边界条件和典型故障场景。
- **范围说明**：列出已实现能力、未实现能力和不适合生产环境的原因。

最终目标不是堆叠功能，而是通过实现、比较、实验和复盘，理解一个系统为什么这样设计，以及它在什么条件下成立。
